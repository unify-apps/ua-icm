This repo builds the Incentive Compensation Management product on UnifyApps — its objects, its automations, and its application pages — driven from Claude Code. Ten minutes here saves you a day.

Last updated 2026-09-03 · lives at docs/START-HERE.html · update it when the shape of the repo changes
The one idea

This repo is not the product

The product lives on the UnifyApps platform. This repo is the written record of it, plus the tools to change it — so anyone (or any Claude session) can read what is true, make a change, and prove the change landed.

Which means the docs are load-bearing, not decoration

Reading docs/ start to finish must land you on the current state of the product. A spec that no longer matches what is deployed is a bug, not a stale doc — so the spec updates in the same commit as the build.

And when a doc and a snapshot disagree, the snapshot wins and the doc is the thing that is wrong.

How assets get built

Two roads to the platform

Everything we build is an object, an automation, or a page. Objects and automations go one way; pages go another. Both use the same _at cookie, and both run entirely on your own machine.

Road 1 · the workhorse
Scripts → REST
Objects and automations
POST /api/workflow-definition/

Plain HTTPS. Write the whole thing as JSON and post it — an automation can be created with all its nodes in one call, which also returns every validation error. Proven 2026-09-02.

Copy every node shape from a snapshot of the same node type — including its groupId branch path. Never guess a shape: a wrong groupId passes validate, runs green, and then silently prunes nodes.

Road 2 · your local server
Devkit → MCP
Application pages
bin/serve start · :3002

Pages are built in a Claude Code session opened in the ua-agent-devkit folder, using 35 typed tools that refuse a bad write.

/start snapshots the page, /done records the session, /restore undoes it. /restore is the only per-page undo that exists — the platform's own history restores the whole app.

Why a page needs different tooling than an automation

An automation is one JSON document — post it and the validator tells you every mistake. A page is 115 block types where almost nothing errors at runtime: a broken binding renders empty, a bad id is a silent no-op, a denied permission hides rather than warning.

So for pages, correctness happens at write time or never. That is what the typed tools are for, and why there is no raw REST path worth using.

The working procedure

Nothing gets built without a spec first

Steps 1 and 2 produce a file, not a paragraph in chat. Chat gets lost; a spec file is what the next person reads.

Step 1

Contract

Agree exactly what it takes in and returns in every outcome, like an API endpoint. Written into docs/.

Step 2

Design

Node list, error paths, what existing callables to reuse, and a row-count estimate at real scale.

Step 3

Build

Write the JSON, copying node shapes from snapshots. Snapshot again immediately after.

Step 4

Test

A regression suite in tests/, green. Plus validate and lint clean — three different layers.

Step 5

Critique

Audit it like a staff engineer. Every finding stands on a runtime fact or a measured number, never a hunch.

Read this before you run anything

The rules that are not negotiable

  • Orbit (UAT) is where we work. Tool is production and is read-only unless a human says otherwise.
  • Never deploy, delete or publish without an explicit human yes in the conversation. Editing a draft is fine; shipping is a separate, gated act.
  • Never test against real pay data. Fixtures are loudly-named participants and periods of our own. A test run that recalculates a real period, or writes a real payout, is the one mistake in this repo that reaches someone's bank account.
  • Schema changes change the data model for everyone, and a property can never be retyped once records exist. Adding is easy; removing is a product decision.
  • Verify writes by re-reading. {"success": true} is a claim about the call, not about the data.

One tool that confuses everyone

graphify does not refresh itself

There are two hooks in .claude/settings.json, but they rebuild nothing — they fire before a search and nudge you to query the graph instead of grepping blindly. Refreshing is manual: graphify update . after code changes (pure parsing, no model, free), or /graphify --update after doc changes.

Output lands in graphify-out/, which is git-ignored on purpose so nobody reviews it as if it were a document. And it reads this repo — so it tells you what the docs say, not what the platform holds. A navigation aid, never evidence.

Intend it in docs/, prove it in tests/, record what is real in snapshots/. Everything else is a tool for moving between those three.
